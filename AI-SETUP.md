# Questbound AI DM connection

## Cheaper turns, a story writer and a usage log — 2026-10-01

- **Play model.** The launcher now suggests `gpt-6-luna` (about half the price of `gpt-5.6-luna` per token). Reasoning is sent as `effort: none` for turns on any reasoning model (`ai-request.cjs`); models without reasoning are not sent the field.
- **Story writer.** `OPENAI_STORY_MODEL` (launcher prompt, remembered in `.questbound-story-model`, changed with `Questbound.cmd -Models`) writes new adventures and heroes with `QUESTBOUND_STORY_REASONING` (default `medium`), an 80-second timeout and room for reasoning tokens. Unset, the play model writes them too. The setup check looks the story model up (`/v1/models/{id}`, no tokens) and reports a wrong ID.
- **Smaller requests.** The scene the model reads is trimmed in `sceneFor` (dm-server.cjs): standing guidance moved into the instructions (cached by the provider), portrait text, the played opening, duplicated place descriptions and conversation entries dropped, skill bonuses as one line each, creature templates only when a creature can appear, and no choices or spell list while narrating a resolved turn. Measured on saved scenes: 15.5k → 10.1k characters at a camp, 14.3k → 8.3k in a fight, 15.3k → 9.4k for a wizard. Validation still uses the full context.
- **Repairs instead of refusals.** A discovery, creature or introduction whose text runs a little long is shortened; a place given a creature becomes a lair. Missing or wrong-kind fields are still refused.
- **Logs.** Live requests append `{mode, model, input, cached, output, reasoning}` tokens to `.questbound-usage.jsonl`; `node dm-report.cjs [--days N]` sums requests, cached share, estimated cost (prices on file for the two luna models) and rejections. Test runs with a fake provider no longer write to either log; the 309 entries logged on 2026-10-01 were test runs except one.
- The running DM picks up `generate` changes at once; the story writer and reasoning settings from the environment apply after a restart with the launcher.

## Current private setup — 2026-09-29

Run `start-dm.ps1` in a private PowerShell terminal. If a DM server is already running on port 8084, stop it with Ctrl+C in its own terminal first. Enter the complete saved secret key at the hidden prompt, not its name or the masked dashboard entry. The launcher now checks one small live DM response before starting the server and offers a private retry if the check fails. A successful check uses a small amount of API usage and does not apply any game action. Keys are not saved to disk by this launcher.

The most recent live check returned HTTP 401 with `invalid_api_key`. A reachable health endpoint with `ready: true` only indicates configuration is present; it does not establish that OpenAI accepts the credential. The running service must be restarted with an accepted key before live play can resume. The setup now distinguishes authentication, permissions, limits, and model errors without logging raw provider messages or key fragments. Mocked setup and server tests passed, as did PowerShell syntax validation; this does not mean the current credential is accepted.

The sections below record earlier implementation checkpoints and may describe superseded behavior.

The app now includes a What do you do? panel and a local Node service using the OpenAI Responses API with structured output. Live requests require your own API account, billing and an available model. No paid request was made during implementation. API keys never go in the Expo app, browser storage, journal or chat.

For now this connection supports the Windows localhost web app. It is not configured for remote phones or public hosting. The service binds to 127.0.0.1:8083 and permits the local app origins on ports 8081 and 8082. It accepts one request at a time, limits request/output size, times out, and disables provider response storage with store:false. This does not claim zero provider retention.

To configure privately: stop an already-running unconfigured DM service; open a PowerShell terminal in this project and run .\start-dm.ps1. It prompts for the API key with hidden input and for your chosen API model ID. The key lives only in the child process environment during that session. Closing the service stops the connection. Do not use an EXPO_PUBLIC variable for secrets. Model access and billing need to be confirmed in your API account before activation. No model or spending plan has been selected on your behalf.

Without credentials, `node dm-server.cjs` runs a health endpoint and returns a clear not-configured message; it does not impersonate live AI or generate canned DM responses. Once configured, the player explicitly presses Ask the AI DM to send their action and a bounded scene summary (character, HP, location, campaign flags, recent log and last 12 journal entries) to OpenAI.

The model returns brief narration and either a currently offered action ID or null. It cannot return arbitrary game-state patches. The app requires the player to apply the suggestion, checks that the scene is unchanged, and passes it to the existing rules engine for validation and actual rolls/resource changes. Spells still use the spell panel and unsupported actions need a human ruling. Narration can still be mistaken: it is labeled AI dialogue, not mechanically authoritative. A player may save the exchange in the journal. No long-term semantic memory, multiplayer server authority, freeform world mutation or live quality evaluation is claimed.

Verified locally with mocked provider responses: schema validation, unknown action rejection, incomplete/error replies, missing credentials, request-origin checks, and HTTP round trip. Live account connectivity and narrative behavior remain unverified until configured.

Official reference: https://developers.openai.com/api/docs/guides/structured-outputs
