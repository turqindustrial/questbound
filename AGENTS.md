# Questbound delivery preferences

- Whenever sharing the playable game, provide separate labeled **Desktop** and **Phone** links, as requested by the user. Keep both on the same current source version.
- Desktop development normally runs at `http://localhost:8081/`. Phone browser access uses `phone-server.cjs` and the current LAN URL, not localhost. Read `.questbound-phone-session.json` for the current link, pairing code and expiry; verify the server is running before presenting it as live. Do not reuse stale IP addresses or codes.
- Rebuild `dist-phone` with `npm.cmd run build:web` after changes before sharing an updated Phone link. `npm.cmd run phone` builds and starts phone access. `start-phone.cmd` provides the same workflow without PowerShell script-policy changes.
- Phone access requires the same Wi-Fi, the PC, the phone gateway, and the existing private DM service running. Saves currently stay in each browser; do not claim cross-device sync or a tested native app.
- Keep the DM service and API credentials private on loopback. Phone clients use the paired same-origin `/api` gateway. Never serve workspace files as static content; only serve the web export directory.
- Test new UI at phone and desktop widths and check phone endpoint routing when changing AI, image, or character generation.
- `Questbound.cmd` (runs `launch.ps1`) starts everything and reuses running services: DM on 8084, shared table (`sync-server.cjs`) on 8086, desktop on 8081 (`desktop-server.cjs` serving `dist-phone`, or Expo with `-Dev`), phone gateway on 8085. It rebuilds `dist-phone` when top-level sources are newer and renews the pairing code when under two hours remain. `-Stop` stops only what it started. Services run in their own hidden consoles with logs in `.questbound-logs/`.
- The API key may be remembered only DPAPI-encrypted in `.questbound-key.dpapi` (user's choice at the launcher prompt); never write it in plain text or pass it on a command line. Never run the key prompt on the user's behalf.
- The shared table keeps one versioned adventure in `.questbound-table/`; phones reach it only through the paired gateway at `/api/sync/*`. Stale writes get 409 and adopt the newer table. Rejected AI replies are logged (mechanical fields only) to `.questbound-diagnostics.jsonl`.
- Internet sharing (`Questbound-Share.cmd` / `launch.ps1 -Share`) runs a Cloudflare quick tunnel to a second gateway instance (`phone-server.cjs --public <https origin>`, loopback port 8087) that accepts only that host/origin, sets Secure cookies, throttles pairing per `CF-Connecting-IP` plus a global 50-wrong-codes-per-hour brake, and caps each session at 60 non-art DM requests per 10 minutes (see Request limits). The share session file is `.questbound-share-session.json` (git-ignored). Never expose the DM, sync or desktop servers directly, and never type an invite code into a page yourself.
- The DM server queues requests (default 3 at once, `QUESTBOUND_DM_CONCURRENCY`); art polls bypass the queue. Restarting the DM needs the user's key: ask the user to run the launcher, never run the key prompt yourself. A DM started with `start-dm.ps1` runs in the user's own PowerShell window and is not in the launcher's pid file: `Questbound.cmd -Stop` does not stop it (and would stop the tunnel, changing the testers' link), so the way to restart it is Ctrl+C in that window, then `Questbound.cmd`. Do not build a way for the DM to relaunch itself with its inherited key: that was tried on 2026-10-02 and stopped by the assistant's safety check; it needs the user's explicit approval. Only `generate` (and the modules it requires fresh) reloads per request; `createServer`'s HTTP layer changes only after a restart. Edit `dm-server.cjs` and `adventure-generator.cjs` in a temp copy, `node --check` and test it (`QB_DM=./copy node verify-dm-stream.cjs`), then copy it over: a syntax error breaks every tester at once.
- Turns and rests (`adventureRules.js`, `classActions.js`, `verify-turns.cjs`): a turn in a creature fight is one action and one bonus action. A healing draught, Second Wind, Lay on Hands, a Monk's strike and bonus-action spells are bonus actions (`bonusOptions`; healing only counts when hurt). After the action, if a bonus action is worth offering, the engine sets `game.actionUsed` (and `game.dodging` for a Dodge) and waits: only a bonus action or `end-turn` is accepted, and a bonus action taken then ends the turn. With nothing to offer, the foe answers at once as before, so tests that expect that use fixtures without a draught or uses (`potions:0`, `resources:{wind:2}`). `short-rest` follows Baldur's Gate 3 (`shortRestLimit`: two between long rests, three for a Bard of level 2+; half HP for the hero and each following companion; Second Wind and Warlock slots back; `game.shortRests`). `long-rest` restores HP, slots, features and short rests and keeps everything else (world, people, pack, feed): never rebuild the adventure with `newAdventure` for a rest. `dmChoices(hero,game,health)` and `quickActions(hero,game,health)` take the hero's health so healing is only offered when hurt. `restWouldHelp` (dmContext.js) treats health null as full hit points, so no short rest is offered to the player or the Dungeon Master when there is nothing to recover: the engine refuses such a rest ("already rested"), and on 2026-10-03 the DM took "catch my breath" as one and the whole turn failed.
- Speaking to the Dungeon Master (`turnMemory.js`, `verify-direct.cjs`): the DM switch beside the message box, or a message starting "DM," / "(ooc)", sends `context.outOfCharacter` (`canRewind`, `lastTurn`); the server answers out of character, changes nothing, and may return `rewind:true`. `Adventure.act(action,conversation,random,{from})` then applies the exchange to the state remembered before the player's last turn (`rememberTurn`/`turnToRewind`: one turn deep, in memory only, never at a shared table). The exchange is an ordinary no-action turn (`conversation.direct`), so it shows in the feed and the journal. When the Dungeon Master cannot be reached, `offline()` in `DungeonMaster.js` tells the host what to start and a guest only that it is not answering (the old "open your private AI setup window" confused phone players).
- Typing on phones (`webLayout.js`): `#root` is pinned to the visual viewport (`--questbound-height`, `--questbound-top`), so the message box rests above the keyboard on Android and iOS. While the message box is focused on a touch device (`touchKeyboard`), `DungeonMaster` reports `onTyping`: the action row, feed header, bottom tabs and (on short screens) the HUD and strips step aside, and the feed stays on its last lines when its height changes. Controls beside a field carry `dataSet={{keepfocus:'true'}}` so a tap does not blur the field first (a blur closes the keyboard, moves the control and loses the tap). Fields in scrolling pages are scrolled into view when the visible height shrinks; dialogs (`data-qb=scrim`) are sized to the visible area. Test by focusing a field and resizing the viewport to about 375×400.
- Lands and maps (`mapRules.js`, `mapLayout.js`, `mapArt.js`, `AdventureMap.js`, `verify-regions.cjs`, `verify-map-layout.cjs`): every written story has its own `story.geography` (where its three starting places lie and which are joined: a line, a fork or a loop), made by `makeGeography` from the story writer's `layout` or from the story id; a save without one keeps the old fixed triangle (`mapCoordinates`). The writer also gives the land a name and a terrain (`story.region`, `story.terrain`; `terrains`), a kind for each of the three places, up to six `landmarks` that `freshStoryGame` puts on the map as unvisited places (`maxLandmarks`), and one or two `lands` beyond this country (`farLandPlaces`: each a region `r1`/`r2` with one known place 15 to 300 miles from the start, joined to it by a road). Places lie a little off their compass bearing (seeded, repeatable). Regions: the home region plus `game.world.regions` (`r1`…, at most 7); a place carries `region` and inherits it from where it was found; the DM's `discovery.region` ({name, terrain}, miles up to 300) opens a new land, and a sequel turns the earlier country into a region of its own. `regionLayout(game,w,h,{region})` lays out one region's sheet and returns `exits` (roads to other regions, drawn to the edge and tappable); `regionMapSvg` draws it to suit the terrain (`mapThemes`: sea along a coast, a river, ranges, woods, pools, cavern walls, all seeded). Long roads are walked eight hours a day (`travelRoute`). `regionLabels` names what fits; `RegionSheet` zooms and `Full map` opens it in a dialog.
- Reactions to the hero's kind (`relationshipRules.js`, `verify-regard.cjs`): `speciesRegard(game,id,hero)` is each person's view of the hero's species (kin, warm, curious, indifferent, wary, scornful, with a reason): written by the story writer or the DM (`regard` on the NPC or person) or drawn from who they are and how that species is commonly met (`reputations`, seeded; a human among humans is indifferent). It sets the first impression (`firstImpressions`, `introducePerson(game,sketch,hero)`), sways Persuasion, Deception and Performance aimed at that person (`regardSway`: +2 to −3, until they are won over), reaches the DM as `regardsYourKind`, and shows in the People panel while it still says something true.
- Portraits and gender (`worldArtRules.js`): NPCs and people carry `gender` (woman, man, other) from the writer or the DM; without it `genderOf` reads their appearance (a hero's description, then backstory). A woman's portrait description opens by saying she has no beard, any facial hair written into it is cut, and her art id gets `-w` so portraits painted before this are painted afresh. Never write a beard into a woman's appearance (the built-in captain once had a "beard ring").
- The story log (`storyLog.js`, `journalRules.js`, `verify-story-log.cjs`): `game.storyLog` holds one short line per major event (place found, reached or returned to, person met, joined or lost, fight begun and how it ended, deaths, grudges and debts, gold and finds, rests, levels, the end of the tale), worked out by `storyEvents(before,after,hero,{action})` and appended by `withStoryLog` in `Adventure.act`; level-ups and new chapters append their own lines. The Log tab shows it newest first; the engine's raw lines sit under "Latest rolls and rulings".
- Inventory and descriptions (`Inventory.js`, `ActionGuide.js`, `descriptions.js`, `verify-descriptions.cjs`): the Inventory tab shows equipment slots around the hero's portrait and everything carried; every item, action chip and spell has a description (`itemDescription`, `actionDescription`, `spellSummary`), and the check fails if anything is left with a generic one. Loot items carry the DM's `note`. `game.wield` (set by Take in hand) makes a carried weapon the main one (`gearedHero` → `equipment.wield` → `weaponAttacks`). The ⓘ chip at the end of the action row opens the action guide.
- The story's main foe (`storyFoeStats` in `storyRules.js`): a written story gets `foeStats` when it begins (18 HP, AC 12, +3, 1d6+1 at level 1, growing with the hero's level; type from the writer's `foeDamageType`); stories from before keep the lighter default. `node balance-check.cjs --foe story` simulates it.
- Long tales (`storyRules.js`, `adventureRules.js`, `dmContext.js`, `verify-chapters.cjs`): a written story has `chapters` (two to six of {title, goal, turn}; `story.chapter` is the one under way) and `leads` (`l1`…`l4`, each {title, hook, done?}); `questState(game)` reads where it stands and `currentGoal` what to do now. The Dungeon Master gets `context.quest` (the chapter under way, what achieving it reveals, the next one, open leads) and never the later chapters (`context.story` is sent without them). It moves the tale on with the choice `story-advance` (the engine's `advanceChapter`: log lines, journal entries, a world fact) and closes a lead with `lead-done:<id>`; `story-complete` is offered and accepted only in the last chapter. Neither is ever a chip (`quickActions` skips them). Every second chapter finished adds to `game.levelsOwed`; `levelUpReady(game,hero)` says when a level can be taken (after victory as before, or owed and out of a fight), and `App.saveAdvancement` takes an owed level where the hero stands (rested, `foeForLevel` grows a foe not yet fought). Owed levels carry into the next tale (`newAdventure`, `carriedBase`). The feed shows chapter, lead and level lines as cards (`describeEvent`), the Quest tab the chapter, the aim and the leads (the player can tick a lead too), and a new chapter is announced with the `area` cue. Stories without chapters play as before. `offeredChoices` keeps the DM's choices to thirty (the server refuses more).
- People speak first (`greetings.js`, `DungeonMaster.engage`, `verify-greetings.cjs`): the Speak chip opens the conversation and asks the Dungeon Master for a scene moment in which only that person speaks (`greeting(game,id,hero).cue`); the stand-in line (`greetingPools`, chosen by grudge, attitude, companionship, then their view of the hero's kind) is used when the DM cannot be reached. `shouldGreet` keeps someone who spoke in the last turn from greeting again, and nobody greets in a fight. The greeting is a trigger turn: no player line, not remembered for rewinds.
- Stories as background jobs (`story-jobs.cjs`, `writeStory` in `dmConnection.js`, `verify-story-jobs.cjs`): the game asks for a story once with `context.job` and then asks after it with `context.mode:'art'` plus `storyJob` every three seconds; see AI-SETUP.md. The story writer's effort is the host's choice in `.questbound-story-effort` (`high` since 2026-10-02, the host's explicit request: do not lower it to save time). A tale takes about three minutes at that effort; `StoryLoading` says so after twenty seconds.
- The title paintings (`assets/title/`, notes in `ART-NOTES.md`): four heroes (warlock purple, cleric yellow-orange, monk white, paladin blue) against a lich (green), wide for computers and a phone on its side, tall for an upright phone. `titleArt(width,height)` in `HomeScreen.js` picks the frame (`wide` covers the window; `tall` and `band` sit between the name and the compact phone menu so the menu never covers the fight) and `App.js` hands its numbers to `webTheme.js` as `--qb-title-*`. An image loaded from a file carries its own pixel size as its style, so `s.backdrop` sets width and height to 100% itself; without that the picture stopped at its own width and wide windows were black on the right (the fault the host reported twice). The saved hero on the wide title is a slim strip in the corner: keep it off the fighters.
- Colours and themes (`theme.js`, `themeRules.js`, `ThemeControls.js`, `webTheme.js`, `verify-theme.cjs`): the player picks the game's colour in Settings → Theme (Red, Orange, Gold, Green, Blue, Purple; per device, `questbound.theme.v1`; asked for by the host on 2026-10-02). Red is the default and the look every colour is written in: dark red on black with purple accents, which the host chose in place of gold on black. Every screen colour is written as its Red value inside `tint(...)` (a single colour, a shadow, or webTheme's whole style sheet); on the web `tint` turns each into a style variable (`var(--qb-e04a5c)`) and one style rule (`#questbound-colours`) gives the variables their values for the chosen theme, so a change repaints at once with no reload. `themeRules.js` sorts each written colour into a family by its OKLCH hue and chroma (the reds are the main colour, the violets the accent, plum near-blacks and greys the neutrals) and each theme says where a family goes (hue, chroma, a lift for bright tones); anything else is the same in every theme: healing green, arcane teal, enemy and danger red-orange (`kept` holds the few that sit near the reds), amber warnings, real gold for coins (`colors.coin`), warm bone text, parchment maps. The token names are from the first look and are kept: `colors.gold` is the main colour, `goldMid` the accent, `goldBright` the pale accent of whatever is selected or lit, `goldDeep`/`goldLine`/`goldFaint` dark main-colour rules. Write a new screen colour as `tint('#e04a5c')`: a family colour written outside `tint()` fails `verify-theme.cjs`, which also checks contrast in every theme. A picture written as text cannot read a style variable, so webTheme's corner filigree and bezel are written out per theme through `themeVariables`. The loading card in `public/index.html` reads the saved theme itself from a table that `node verify-theme.cjs --write` regenerates (run it after changing a theme or the card). To look at a theme in the test browser, set `QB_THEME` for the capture script or store `{"theme":"green"}` under the key. The app icon and the pairing page stay red in every theme. The pairing page in `phone-server.cjs` carries its own copy of these colours (it is served before the game is), so a change of theme must be made there too and both gateways restarted. The app icon is `assets/title/icon.html`, photographed at each size by `node make-icons.cjs`; raise `?v=N` in the icon links when it changes (see `assets/title/ART-NOTES.md`).
- Fit (`ui.js`, `GameHud.js`, `AdventureMap.js`, `webLayout.js`): on phones `Segmented` and the side tabs size each tab to its word, `GameButton` sets its lettering tighter, the pause menu scrolls and (on a phone held sideways) shows four cells to a row, and the full map puts the row of lands beside the heading on short screens. Rows that scroll sideways turn under a mouse wheel. At window heights under 700 the action chips stay on one row and the narrator's heading is dropped. The browser pane's screenshots can come back cropped after a resize or a script reload: navigate afresh, or measure with `getBoundingClientRect`, before trusting one.
- Dice in the feed (`TurnPlayback.js`): `DieFace` tumbles in, flickers through numbers and lands; `RollNumber` rolls damage and healing up; both only for the live turn and never with reduced motion. A check card names the skill rolled (`describeEvent` → `check`).
- Sound (`audio.js`, `verify-audio.cjs`): the score is pads, a bowed bass, felted keys in a fixed figure and a flute or horn singing composed phrases (A A B A, in key, landing on chord tones); nothing is plucked or ticked, every voice has an attack of at least a hundredth of a second, and the hearth no longer crackles steadily. Keep it that way: the player called the old plucked score "clickety clackety".
- Loading screens say little by design (`SceneTransition.js`, `StoryLoading.js`, `DynamicArt.js`): a place name or "One moment", a line that fills, a way to continue. Do not list what is being generated. (A new tale takes minutes: after twenty seconds the screen says once that a long tale is written with care.)
- Loadouts (`weaponRules.js`, `verify-loadouts.cjs`): kits follow the 2024 starting equipment exactly (checked item for item). A hero's main weapon is the best close-range weapon they carry for their own scores (`readyLoadout`, `weaponAttacks` order; class order in `classWeapons` settles ties), and `loadoutWarnings` names ill-fitting gear (Chain Mail under Strength 13, heavy weapons, the wrong Fighter kit).
- Developer options (`DeveloperOptions.js`, `verify-developer.cjs`): at the bottom of the character builder, behind the developer code `6969` (a convenience gate for testers, not a secret), `form.level` and `form.devScores` (each 1–20, with `devLevel`) replace level 1 and the standard array; `finalScores` returns them plus improvements from later level-ups, and the hero passes the same validators as any other.
- Models and request size (`ai-request.cjs`, `verify-dm-trim.cjs`): the launcher suggests `gpt-6-luna` for play (`OPENAI_MODEL`, remembered in `.questbound-model`) and an optional story writer (`OPENAI_STORY_MODEL`, `.questbound-story-model`; `Questbound.cmd -Models` changes both without the key) that `generate` uses for `mode:'adventure'` and `mode:'character'`. A running DM reads both files on every live request (`liveModels` in `dm-server.cjs`), so a change of model takes effect at once with no restart and no key; the play model also drives the image tool. Since 2026-10-02 everything runs on `gpt-6-luna` (no `.questbound-story-model`). A long tale takes about three minutes on it at high effort (written as a background job), 25 to 30 s at low; at medium it no longer fits in one 80-second request. To compare models on whether they act when asked, score them with a probe of ordinary requests (go to a known place, search, explore) before switching: both scored about three in four after the `WHAT IS TRUE NOW` instructions were added. A reply that starts two game actions keeps the first (`generate` repairs it) instead of being refused. `modelOptions(model,effort)` adds `reasoning.effort` only for reasoning models (GPT-5 and later, o-series): turns use `QUESTBOUND_DM_REASONING` (default `none`), heroes `QUESTBOUND_STORY_REASONING` (default `medium`, with an 80 s timeout and 6000 more output tokens of room), and stories the effort in `.questbound-story-effort` (read live by `storyEffort`; else that same setting). `sceneFor` trims what the model reads (standing guidance lives in `contractInstructions`, in the cached prefix; portraits, the opening, duplicated place and conversation text and phase-irrelevant parts are dropped) while every validator still sees the full `body.context`; `repairedDiscovery`/`repairedCreature`/`repairedIntroduce` shorten overruns instead of refusing the reply. Live requests append token use to `.questbound-usage.jsonl` and rejections to `.questbound-diagnostics.jsonl`; runs with a fake `fetchImpl` log nothing. `node dm-report.cjs [--days N]` sums cost and rejections; `node balance-check.cjs` simulates fights per ready-made hero, level and creature.
- Streaming and number checks (`verify-dm-stream.cjs`, `verify-cloud.cjs`): `askDm(..., {onNarration})` sends `stream:true`; a restarted DM answers game turns as NDJSON (`{narration}` lines, then `{reply}` or `{error}`), the gateways pass it through, and `DungeonMaster.js` shows the draft while busy. An older DM answers plain JSON and nothing changes. `checkedHp` softens HP figures in narration and dialogue that the context or the engine's HP lines do not support ("down to 3 HP" becomes "badly hurt").
- Holding the Dungeon Master to what the player asked (`dm-intent.cjs`, the second look in `generate`, `verify-dm-intent.cjs`, `dm-probe.cjs`): `context.now` is a few plain sentences the game works out (where the player is, whether a fight is on, what became of the foe, which journeys are on offer) and the model reads first; `WHAT IS TRUE NOW` tells it to believe them over the premise, journal and recent events. After an ordinary reply, `secondLook(body,reply)` checks it against the player's words: a plain request the game offers (a known place by name or by a word only it has, somewhere new while `canDiscover`, a rest, a draught, a lead handed in) that the reply did not act on, a known place chosen when the words asked for somewhere new, or a fight spoken of as still going on when none is, gets one more request with `LOOK AGAIN:` after the standing instructions (cached) and `low` thinking; if the second reply still does not act and the request is unmistakable (`sure`: a whole place name or a six-letter word only it has, no question, no hedge such as tell/ask/if/later/tomorrow), the game starts the action itself with a one-line telling (`settled`). Leads are never settled by the game. Questions, plans, speech, fights, spell rulings, resolved turns, scene cues and out-of-character talk are left alone. A reply that is not JSON is first repaired when the fault is small (markdown fences or prose around the object: `repairedJson`, noted as a second look "repaired"), else refused and recorded in the diagnostics with its shape only (`replyShape`: length, how it starts and ends, the provider's output item types, refusal or incomplete; never its words), and a refusal is told to the player as such ("declined to answer", not retried). A reply that cannot be used (unparseable, outside the schema or the rules) is asked for once more with the reason; a provider rate limit (`rate_limit_exceeded`) is waited out twice. Second looks are logged to `.questbound-diagnostics.jsonl` (`secondLook`, `outcome`) and counted by `dm-report.cjs`. `.questbound-dm-effort` sets how hard the play model thinks about ordinary turns, live (`turnEffort`; default none). Measure with `node dm-probe.cjs [rounds]` (acts when asked) and `node dm-judgment.cjs [rounds]` (judges well: grudges and bonds, deeds recorded, gold and goods, fight tempo, resolved results told as they fell; 24 situations, 48 of 48 on 2026-10-02) against the running DM (paced at one request every three seconds, so it never uses the provider's per-minute allowance that players need: an unpaced probe did on 2026-10-02): 24 of 30 before the second look, 29 of 30 after; the scratch chapter probe closed leads 16 of 16. `knownPlaces` now carry a compass `bearing` from where the hero stands.
- Legal (`legalText.js`, `Legal.js`, `verify-legal.cjs`, `PRIVACY.md`, `TERMS.md`, `public/privacy.html`, `public/terms.html`, `public/permissions.html`, `PERMISSIONS.md`): the privacy policy, terms of use and licence notices are written once in `legalText.js` and shown in the game (Settings → About, the title screen's Privacy · Terms, a line under account creation) and as pages the phone gateway serves before pairing (linked from the pairing page). `node verify-legal.cjs --write` regenerates the pages and documents; the check asserts that the words match the code (200 recovery-code copies, 180-day sign-ins, hashed email and password, Google Fonts, Cloudflare, OpenAI), that both SRDs are attributed in their licences' exact words, and that no file names an unlicensed book. The host is the controller; the developer receives no data. Playable content: the SRD 5.2 and 5.1 (Half-Elf), one SRD subclass a class, plus the Artificer (four specialities) and the Goblin at the host's choice (2026-10-02), all in Questbound's own words: never copy text from a book that is not an SRD, never name one in the game, and never use another publisher's settings, creatures or characters (the Dungeon Master and story writer carry an OWN WORLD rule; `Underdark` is not SRD wording). The game is for players 16 and over. The policy's figures must change with the code: edit `legalText.js` in the same change. The permissions agreement (`permissionsAgreement` in `legalText.js`, `agreementRules.js`, `Agreement.js`, `verify-agreement.cjs`): after the launch screen, a browser that has not agreed to the current `legalUpdated` sees seven points (words go to an AI, saves in this browser, copies on the host, feedback and service records, sound and full screen, age and conduct, changing your mind) with one tap to agree; the record in `questbound.agreement.v1` is the version (the `legalUpdated` date) and the time, so changing the texts asks everyone again. The dialog steps aside while the Legal screen is open and returns after it. Legal's Permissions tab says when this browser accepted.
- Accounts (`accounts.cjs`, the `/account-*` routes of `sync-server.cjs`, `accountRules.js`, `AccountSettings.js`, `verify-accounts.cjs`): an email and a password keep a player's hero and adventure in `.questbound-accounts/` (git-ignored) under a hash of the email, with the password as a salted scrypt hash and sign-in tokens as hashes; the email itself is never written down, nothing is sent to it (there is no mail service) and it is not verified. Wrong passwords are counted per account (5 in 15 minutes), per caller (12; the phone gateway names the visitor in `X-Questbound-Client`) and overall (200 an hour), and refused for a while; tokens last 180 days, 8 per account; at most 500 accounts. The game saves to the account a few seconds after each local save (`scheduleCloudSave` → `saveToAccount`), alongside the recovery-code copy. Signing in to an account that already holds a save puts the device on `hold`: nothing is uploaded until the player chooses to load the account's adventure (the current hero is set aside first) or keep this device's. Changing the password signs the other devices out; deleting the account removes its save. The host resets a forgotten password with `node accounts.cjs reset-password <email>` (the player creates the account again with the same email and keeps the save) and removes one with `remove`. The title screen offers "Keep your progress safe: create an account" while an adventure exists and no account is signed in (`unprotected`; `titleArt` makes room for it). Settings puts the account first. The sync server and both gateways must be restarted when these server files change.
- Request limits (`limiter` and `limits` in `phone-server.cjs`, `quota`/`overLimit` in `sync-server.cjs`; `verify-phone.cjs`, `verify-cloud.cjs`, `verify-accounts.cjs`): every gateway request is counted in memory in sliding ten-minute windows and refused with 429 and a `Retry-After` header past its allowance. Per paired browser (cookie hash): `dmLimit` turns (120 at home, 60 on the shared link; `mode:'art'` illustration and story checks count against `artLimit` 600 instead, and the game waits a few seconds on a 429 there), `syncLimit` 600 `/api/sync/*` requests (the table polls every 2.5 s), 20 recovery-code loads, 10 password changes or deletions; per visitor address (`client(req)`, the tunnel's `CF-Connecting-IP`): 5 sign-ups an hour, 20 sign-ins, `requestLimit` 3000 requests of any kind (checked before anything else, pairing page included); for the gateway as a whole `dmTotal` 600 turns. The table service counts again per `X-Questbound-Client` (`this-pc` for the host's own browsers) with roomier `quota` figures that tests override with `limits`. Messages for turn caps must never match the game's busy-DM retry test in `dmConnection.js` (`Please wait before asking|busy with other players`), or the game would hammer the cap. `info.limits` reports the figures (written to the session files).
